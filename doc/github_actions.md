# Как запустить проект на GitHub Actions

Пошаговая инструкция: от пустого репозитория до работающего дашборда
на GitHub Pages. Все команды проверены на Windows, в PowerShell.

---

## 0. Что уже готово в репозитории

| Что | Где |
|---|---|
| Скрипт конвейера | `scripts/run_pipeline.sh` |
| Workflow | `.github/workflows/main.yml` |
| Исходный набор данных | `data/motor_data14-2018.zip` (6,4 МБ) |
| Пин зависимостей | `requirements-lock.txt` |
| Тесты | `tests/` (342 теста) |

Распакованный CSV (48 МБ), батчи, модели и отчёты в репозиторий **не
попадают** — они перечислены в `.gitignore` и создаются прогоном.

---

## 1. Создать репозиторий и загрузить код

```powershell
cd "Z:\Магистратура\Семестр 3\AgentSlop\MLOps_New"
git init
git add .
git commit -m "MLOps-конвейер: волны 0-3"
```

Затем создайте **пустой** репозиторий на github.com (без README и
`.gitignore` — иначе push будет отклонён) и свяжите его:

```powershell
git remote add origin https://github.com/<ВАШ_ЛОГИН>/<НАЗВАНИЕ>.git
git branch -M main
git push -u origin main
```

**Важно:** если `git` не установлен, поставьте его с
<https://git-scm.com/download/win> и перезапустите терминал. На
сервере GitHub он не нужен — он нужен только для первого `push`.

Проверьте, что архив данных действительно попал в коммит:

```powershell
git ls-files data/
```

В списке должен быть `data/motor_data14-2018.zip`. Если его нет —
проверьте `.gitignore`: строка `data/*.csv` архив не затрагивает, но
файл должен существовать на диске.

---

## 2. Проверить, что workflow виден GitHub

Откройте репозиторий → вкладка **Actions**. Должна появиться строка
**MLOps CI Pipeline** со списком workflow.

Если её нет:

1. Проверьте, что файл лежит именно по пути
   `.github/workflows/main.yml` (регистр и имя каталога важны).
2. Проверьте, что ветка называется `main`. Переименуйте:
   `git branch -M main && git push -u origin main`.
3. Откройте workflow вручную: **Actions → MLOps CI Pipeline → Run
   workflow**.

---

## 3. Первый запуск

**Actions → MLOps CI Pipeline → Run workflow** → поле **Run workflow**.

| Поле | Значение | Смысл |
|---|---|---|
| `n_batches` | `12` | Сколько батчей обработать за прогон |
| `refresh` | `true` для первого раза | Начать с нуля, не брать состояние из кэша |

В workflow три job, они идут последовательно:

```
test  →  train  →  publish
301      48        дашборд
 тест    батчей    на Pages
```

### Что смотреть в каждом

**`test`** (~40 секунд) — компиляция, валидация `config.yaml`, проверка
самого workflow и 342 теста. Упало здесь — правьте до обучения:
дальше запускать бессмысленно.

**`train`** (~6 минут при 12 батчах, ~15 при 48) — основная работа.
Прогресс видно в раскрывающемся списке шагов; подробный лог лежит в
артефакте `training-logs`.

**`publish`** — развёртывание сайта. Если Pages не настроен, job
закончится предупреждением, а workflow останется зелёным: публикация
не должна ронять обучение.

---

## 4. Включить GitHub Pages

Это нужно сделать один раз. Без этого job `publish` не публикует
ничего: он завершится зелёным с предупреждением, а дашборд останется
доступен в артефактах прогона.

1. **Settings → Pages**.
2. **Build and deployment → Source**: выберите **GitHub Actions**.
3. Нажмите **Save**.

Через минуту-полторы адрес сайта появится там же, в поле URL, и в
среде `github-pages` на вкладке **Environments**. Он будет вида
`https://<ЛОГИН>.github.io/<НАЗВАНИЕ>/`.

Проверить можно так же: **Actions** → последний прогон → job
**Публикация дашборда (GitHub Pages)** → ссылка в описании окружения.

### Если job упал с «Get Pages site failed: Not Found»

Это самая частая первая ошибка, и она **не означает**, что в репозитории
чего-то не хватает. Pages — настройка самого репозитория, а не файл в
нём, поэтому в коммит её положить нельзя.

Признак: в логе `actions/configure-pages` —

```
Error: Get Pages site failed. Please verify that the repository has
Pages enabled and configured to build using GitHub Actions
Error: HttpError: Not Found
```

Что делать: ровно то, что в разделе 4 выше — **Settings → Pages →
Source → GitHub Actions → Save**. После этого можно не перезапускать
прогон, а нажать **Run workflow** вручную, либо дождаться ближайшего
срабатывания расписания.

Автоматически включить Pages из workflow нельзя: параметр
`enablement: true` у `actions/configure-pages` требует персональный
токен (PAT) со.scope `repo`, а не встроенный `GITHUB_TOKEN`. Создавать
секрет ради одной настройки нецелесообразно.

После исправления job останется зелёным в любом случае: если Pages
выключены, он теперь не падает, а пишет в сводку запуска, где искать
дашборд в артефактах.

> На бесплатном плане Pages работает для публичных репозиториев.
> Для приватного репозитория нужен тариф GitHub Pro/Team — иначе
> публикация не пройдёт, но на результат обучения это не влияет.

---

## 5. Где смотреть результаты

Все результаты — в интерфейсе конкретного прогона, а не в самом
репозитории. Откройте **Actions → MLOps CI Pipeline →** нужный запуск.

### Сводка на странице прогона

Блок **Summary** внизу: сколько батчей обработано, список моделей,
начало последнего отчёта и состав опубликованного сайта. Это читается
быстрее, чем лог.

### Артефакты

Внизу той же страницы, раздел **Artifacts**, скачиваются кнопкой
(браузер сам их распакует):

| Артефакт | Содержимое |
|---|---|
| `training-logs` | полный лог прогона |
| `reports` | текстовый и JSON-отчёты (`summary_*.txt/.json`) |
| `models` | модели: продуктовая, последние версии, сборщик данных |
| `metadata-and-dashboard` | метаданные по каждому батчу, правила, `dashboard.html` |
| `site` | собранный сайт целиком |

### Сайт

`https://<ЛОГИН>.github.io/<НАЗВАНИЕ>/` — визитка со сводкой прогона
и ссылкой на дашборд истории обучения.

## 6. Дальнейшие сценарии

### Дообучение на новых батчах

Запустите workflow вручную с `n_batches = 12` и `refresh = false`.
Состояние поднимется из кэша, и обучение продолжится с того места, где
остановилось.

### Полный перезапуск

`refresh = true` — состояние, модели и метаданные удаляются, обучение
идёт с нуля. Так же происходит автоматически при `push` в `main`:
изменился код — проверяем, что система по-прежнему обучается целиком.

Локально то же самое делает флаг сброса:

```powershell
python run.py -mode init -reset
```

Без него повторный `init` **не трогает** уже накопленное обучение: если
набор данных не изменился, он лишь заново создаёт файлы батчей (в CI
они не сохраняются в кэше) и печатает, сколько батчей уже обработано.
Именно это делает возможным дообучение по расписанию. Если данные
изменились, прогресс сбрасывается сам, с предупреждением.

### Новые данные извне

```powershell
python -m src.collector --describe
python -m src.collector --append data/new_month.csv
python run.py -mode update -n 1
```

Сборщик проверяет схему, разбирает даты и отказывается принимать файл
за уже известный месяц. `-mode sync` добавляет принятые батчи в
состояние; `update` делает это и сам.

### Расписание

Workflow срабатывает по cron `17 3 * * 1-5` — будни в 03:17 UTC. Минута
выбрана не «в час»: в это время на публичных репозиториях меньше всего
одновременных запусков. Каждое срабатывание дообучает очередные батчи.

Расписание видно только в коммите, зафиксированном в `main`. Чтобы его
отключить или сдвинуть, правьте секцию `schedule` в workflow.

## 7. Если прогон упал

| Симптом | Причина | Что делать |
|---|---|---|
| Упал `test`, ошибка конфигурации | Невалидный `config.yaml` | Запустить локально `python run.py -mode init`, прочитать сообщение |
| Упал `train` на `init` | Не загружен архив данных | `git ls-files data/` — должен быть `.zip` |
| Упал `publish` | Pages не включены в репозитории | `Settings → Pages → Source → GitHub Actions` (подробно — в разделе 4) |
| Артефактов нет | `train` упал до их выгрузки | Смотреть лог в `training-logs` |
| Кэш состояния пуст, обучение с нуля | Кэш истёк (7 дней без обращений) или это первый `push` | Ожидаемо; состояние восстановится со следующего сохранения |

Отдельно о сообщении «Обработано батчей: 0»: это **не** ошибка. Оно
означает, что все батчи уже обработаны. Чтобы обучить заново, поставьте
`refresh = true` или увеличьте `n_batches`.

Подробный разбор логов:

```powershell
# Локально с тем же кодом, что и в CI
bash scripts/run_pipeline.sh 12
```

Скрипт — тот же самый, что вызывается в workflow, и в нём включён
`set -euo pipefail`: упавший батч останавливает прогон, а не прячется
за зелёным статусом.

## 8. Проверка перед сдачей

```powershell
python -m pytest tests -q                    # 342 теста
python -m tests.check_workflow .github/workflows/main.yml
python run.py -mode init
python run.py -mode update -n 2
python run.py -mode summary
python run.py -mode publish
python run.py -mode inference -file data/raw_batches/batch_2018-06.csv
```

Последнюю команду стоит выполнить: она доказывает, что сохранённая
модель действительно работает на данных извне, а не только на том, на
чём обучалась.
