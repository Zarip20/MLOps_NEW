# Постановка задачи и проектирование системы

Документ описывает, что система делает и почему именно так. Все числа
взяты из артефактов последнего прогона: `reports/summary_*.txt`,
`data/metadata/*.json`, `reports/meta.json`, `reports/preprocessing_sweep.json`.
Проверить любое утверждение можно командой из раздела 12.

Историю изменений и найденные дефекты см. в [`../PLAN.md`](../PLAN.md).

---

## 1. Источник данных

- **Набор:** Ethiopian Insurance Corporation, страхование транспортных
  средств, июль 2014 — июнь 2018.
- **Формат:** CSV, **508 499** строк, 16 колонок, архив 6,4 МБ.
- **Временная колонка:** `INSR_BEGIN` — по ней батчи режутся помесячно,
  получается **48 батчей**.
- **Целевая метка:** `HAS_CLAIM` = 1, если `CLAIM_PAID` заполнен.
- **Раскладка классов:** доля положительного класса падает с **11,08 %**
  (батч 0) до **2,38 %** (батч 47). Это тренд, а не аномалия, и он
  отслеживается отдельно от дрейфа признаков.

**Источников может быть несколько** (1.b.ii). Список задаётся секцией
`sources` в `config.yaml`; каждый источник приводится к общему
контракту (архив или CSV, своё имя, свой префикс имён батчей) и
складывается в один поток. Если секция не задана, работает прежняя
пара `paths.source_zip` / `paths.source_csv`. Префикс обязателен при
нескольких источниках: два набора за один месяц иначе переписали бы
друг друга.

## 2. Задача

Бинарная классификация: произойдёт ли страховой случай по полису.

## 3. Этапы конвейера

Порядок этапов задан в `Pipeline._process_batch` и не меняется:
качество → очистка → ассоциативные правила → EDA → дрейф → признаки →
обучение → реестр → очистка моделей → накопление → интерпретация →
метаданные.

### 3.1. Сбор и эмуляция потока

- `split_all_sources()` режет все включённые источники на батчи и
  складывает их в один список по возрастанию периода.
- Батчи лежат в `data/raw_batches/batch_YYYY-MM.csv` и содержат
  **все** колонки источника: очистка применяется позже, чтобы хранилище
  сырых данных оставалось сырым.
- Состояние — `state.json`: версия схемы, хэш данных, список батчей,
  индекс последнего обработанного, история запусков.
- **`-mode init` идемпотентен.** Набор данных не изменился — прогресс
  сохраняется; батчей не хватает (в CI каталог не входит в кэш) — они
  пересоздаются, и прогресс снова сохраняется. Сброс происходит только
  при смене данных или по флагу `-reset`. Без этого расписание
  дообучения каждый раз обучало бы систему с нуля.

Приём новых данных извне — сериализуемый сборщик `src/collector.py`:
`python -m src.collector --append файл.csv`. Проверяет схему, разбирает
даты, отказывается затирать уже известный месяц.

### 3.2. Качество данных

На каждый батч считаются: полнота (общая, по колонкам, по строкам),
валидность типов, своевременность (минимум, максимум, разрывы),
нарушения статических правил, динамических ассоциативных правил и EDA
(профиль, распределения, кардинальность, доля сентинельных нулей).
Результат — `data/metadata/quality_<idx>.json`.

**Статические правила** заданы декларативно в `config.yaml` и
вычисляются интерпретатором без `eval`: оператор выбирается из
замкнутого набора (`ge`, `in`, `notna`, `positive` и другие), значение
приходит данными, а не кодом. Правило для грузовых транспортных
средств проверяет `TYPE_VEHICLE` по списку `Truck`, `Tanker`,
`Trailers and semitrailers` и требует `CARRYING_CAPACITY > 0`.

**Ассоциативные правила** (`fpgrowth`, 5 правил, параметры в конфиге)
генерируются **один раз** — на первом батче — и сохраняются в
`data/rules.json`. На всех следующих батчах доля нарушений считается по
этому **фиксированному** набору, иначе батчи были бы несопоставимы:
при пересборке правил на каждом батче «нарушение» означало бы разное
при одном и том же качестве данных. Доля считается среди строк,
**удовлетворяющих антеценденту**, — иначе метрика размывалась бы и не
означала бы заявленного.

Найденные правила отвечают за реальные дефекты разметки, а не за
случайные совпадения: `TYPE_VEHICLE = Special construction` →
`USAGE = Special Construction` (lift 25) и `MAKE = INTERNATIONAL USE`
→ `TYPE_VEHICLE = Special construction` (lift 27) — расхождение регистра
в одной и той же категории.

### 3.3. Очистка

- Строки с долей пропусков выше порога удаляются.
- Строки, нарушающие правила, удаляются, если доля нарушений не выше
  порога. **На этих данных очистка удаляет около 6,8 % строк** — это
  исправленный дефект, а не поломка: правило для грузовиков обязано
  отбрасывать строки с пустой грузоподъёмностью. Величина и доля
  фиксируются в метаданных.
- Категории нормализуются по регистру (`truck` → `Truck`).
- `INSURED_VALUE == 0` — **значимое значение** (45,5 % строк), а не
  пропуск. Импутация для этих нулей не вводится, производные признаки
  их не штрафуют. Обоснование и следствия — в разделе 9.

### 3.4. Признаки

12 инженерных признаков поверх исходных колонок: возраст ТС, месяц,
квартал, год, день года, длительность полиса, отношение
`INSURED_VALUE/PREMIUM`, флаги сентинельного нуля и пропуска грузоподъёмности,
логарифмы тяжёлых хвостов. Список берётся из `config.yaml` и
**дополняется из самого препроцессора** — он объявляет свою схему, и
она надёжнее пересборки из конфигурации.

## 4. Модели

Четыре модели намеренно разной природы (4.a, 4.b.ii):

| Модель | Роль | Обучение | Гиперпараметры |
|---|---|---|---|
| `lr` | интерпретируемая базовая | с нуля | `C=1.0`, `max_iter=1000`, `class_weight=balanced` |
| `dt` | ловит нелинейности | с нуля | `max_depth=10`, `min_samples_split=20`, `min_samples_leaf=10`, `class_weight=balanced` |
| `rf` | устойчива к разреженности | с нуля | 60 деревьев, `max_depth=12`, `class_weight=balanced_subsample` |
| `mlp` | единственная с дообучением | **`partial_fit`** | `[50,25]`, `relu`, `adam`, `max_iter=300`, 5 эпох на батч |

Накопительное хранилище (`data/processed/`) используют `lr`, `dt`,
`rf`: они переобучаются на всей истории train-частей. `mlp` историю не
переигрывает — она дообучается только на новых данных, в этом и есть
смысл инкрементального обучения.

**Дисбаланс компенсируется ровно одним механизмом.** Если у
конструктора задан `class_weight`, веса образцов не применяются:
одновременное использование обоих компенсировало бы дисбаланс дважды
и стоило дереву 0,08 f1 (0,237 → 0,161).

## 5. Валидация

- Схема: hold-out **20 % текущего батча**, со стратификацией по метке,
  откладывается **до** обучения. Валидация не попадает ни в обучение
  моделей, ни в обучение препроцессора.
- Метрики: precision, recall, f1, ROC-AUC, accuracy, матрица ошибок.
- Выбор по **f1** — по условию задания.

Это было исправление критического дефекта: раньше модель обучалась на
всей матрице, и только потом данные делились, так что метрики
измерялись на данных, участвовавших в обучении.

**Ограничение f1, о котором стоит знать** (раздел 9).

## 6. Реестр версий и гейт качества

`models/registry.json` хранит **все** версии: номер, модель, батч,
метрики, причину отклонения, дату. Продуктовая модель переключается не
автоматически, а через гейт:

| Правило | Порог |
|---|---|
| минимальный f1 | 0,05 |
| минимальный ROC-AUC | 0,60 |
| допустимое падение f1 к текущей продуктовой | 0,15 |
| PSI выше этого — версия не выводится в продуктив | 0,45 |

Отказ не удаляет версию из истории: без этого нельзя понять, почему
качество упало.

**Файлы** старых версий ограничены (`registry.keep_artifacts_per_model: 5`),
**записи** реестра сохраняются все: на 48 батчах каталог `models/` без
ограничения весил бы около 160 МБ, из которых 145 МБ — случайный лес.
Продуктовая версия не удаляется никогда, даже если она старше всех.

## 7. Дрейф

- **Дрейф признаков:** PSI по числовым признакам и KS по каждому,
  пороги в конфиге, статус `ok` / `warn` / `alert` пишется в
  метаданные и **не роняет конвейер** — это решение, а не исключение.
- **Дрейф метки:** доля положительного класса и её изменение
  отслеживаются отдельно. За прогон она падает на 78,7 %, и это тренд,
  а не аномалия.
- Категориальный PSI по умолчанию выключен: на этих данных он давал
  0,98 для `SEX` (норма 0,05) — то есть оценивал не сдвиг, а
  несопоставимость месячных срезов.

Порог PSI выбран по измерениям, а не взят из учебника: выражена
сезонность (доля страховых случаев в июле 11 %, в феврале 5 %), PSI
между соседними месяцами держится в диапазоне 0,15…0,45, и «учебный»
0,25 помечал бы alert на большинстве батчей, не различая норму и
аномалию.

## 8. Интерпретация

- Линейная регрессия: коэффициенты.
- Дерево: карта решений и важность признаков.
- Случайный лес: важность по убыванию важности ( impurity).
- Нейросеть: для первого скрытого слоя — среднее `|W|` по единицам,
  нормированное на вход первого слоя.
- Согласованность между моделями: доля признаков, попавших в топ-N
  у всех сразу.

## 9. Что система НЕ умеет и какие у неё ограничения

Этот раздел — обязательная часть отчёта: без него цифры выше выглядят
лучше, чем система есть.

### 9.1. Модели систематически завышают долю положительного класса

Замерено на всех 48 батчах: модели предсказывают положительный класс
в **34…69 %** строк при фактических **6,6 %** — превышение в 5–10 раз.

Причина: f1 максимизирует recall, а дисбаланс компенсируется весами, и
модель учится называть положительным всё подряд. Для f1 это выгодно, для
бизнес-решения — бессмысленно: страховщику предъявляют вчетверо больше
полисов, чем случилось.

**Что с этим сделано.** Введён калиброванный порог: решение принимается
по квантилю вероятностей, а не по 0,5. На последнем батче порог
подбирается к **0,827** под долю 2,4 %, а без калибровки модель дала бы
18,8 % положительных. Порог выбирается под **текущую** долю класса
(`target_positive_rate: auto` — читается из последних батчей), потому
что фиксированное число устарело бы молча.

**Чего это не решает.** Калибровка приводит долю решений к нужному
уровню, но не улучшает precision: отбираются те же примеры, что и раньше,
только порог отсекает худшие. Радикальное решение — отказ от компенсации
по весам и обучение на несмещенных данных; оно не проверено, и в текущем
прогоне не применяется.

### 9.2. Выбор предобработки сделан на одной модели

Перебор вариантов (`median`/`mean` × `standard`/`robust` × top-K `MAKE`)
выполняется на **одной дешёвой модели `lr`** и на том батче, где
препроцессор обучается заново. Дерево, лес и нейросеть реагируют на
масштаб и импутацию иначе, и перенос выбора на них автоматически не
выполняется. Результаты перебора — в `reports/preprocessing_sweep.json`
и в отчёте, раздел 11, — и решение можно проверить и оспорить.

### 9.3. Оценка влияния гиперпараметров ограничена

Гиперпараметры заданы один раз и не меняются, поэтому по постоянным
настройкам их влияние **не оценивается** — сравнивать нечего.
Анализ Meta Learning так и пишет и отдельно перечисляет непроверенные
настройки, вместо того чтобы выдать правдоподобную «важность» без
смысла. Оценивается то, что меняется само: объём накопленных данных,
достигнутое число итераций, режим обучения, доля положительного
класса, номер батча.

### 9.4. Другие ограничения

- Признаки зависят от того, какие колонки встретились на **первом**
  батче: `MAKE` даёт 284 категории там и 161 в последнем, поздние
  значения схлопываются в нули. Переобучение препроцессора на новых
  данных возможно, но не выполняется автоматически.
- Дисбаланс 6,6 % положительного класса при 20 % hold-out даёт
  валидацию в несколько сотен положительных примеров на последних
  батчах. Метрики устойчивы, но их доверительные интервалы широкие.
- Ассоциативные правила фиксированы на первом батче — это сделано
  ради сопоставимости батчей, но означает, что закономерности,
  проявившиеся только в поздних данных (например, в 2018 году),
  обнаружены не будут. Пересборка правил по требованию — удаление
  `data/rules.json` и повторный `-mode init`.
- Инференс при недоступной продуктовой модели переходит на запасную, а
  при нерабочем препроцессоре выдаёт константу «случаев нет». Обе
  деградации помечаются в отчёте инференса, но качество такого
  прогноза не гарантировано.

## 12. Архитектура

Слои разделены явно, и разделение проверяется тестами по исходникам
(`tests/test_architecture.py`), а не держится на договорённости:

```
run.py                 контроллер ввода: разбор аргументов, коды возврата
  └── src/pipeline.py  оркестратор: порядок этапов, ничего не считает сам
        ├── домен      data_quality, rules, association, drift, features,
        │              preprocessing, training, registry, storage
        └── src/ports.py  порт представления (name + render)
              └── src/views.py  адаптеры: отчёт, дашборд, сайт, анализ
```

`run.py` не импортирует ни одного доменного модуля; доменные модули не
знают про оркестратор; слой вывода обращается к конвейеру только через
порт. Новое представление добавляется регистрацией одной строкой.

## 13. CI/CD

Workflow **MLOps CI Pipeline**: три job `test → train → publish`.

- **Триггеры:** push и pull request в `main`, ручной запуск, расписание
  `17 3 * * 1-5` (минута не «в час» — в это время меньше всего
  одновременных запусков).
- **Кэш состояния:** `state.json`, `models/`, `data/metadata/`,
  `data/processed/`, `data/rules.json`. Без него каждый запуск обучал бы
  систему с нуля и дообучение было бы невозможно.
- **Публикация:** сайт разворачивается на GitHub Pages. Если Pages не
  включены, job остаётся зелёным с предупреждением: публикация не
  должна ронять обучение.
- **Артефакты прогона:** логи, отчёты, модели, метаданные, дашборд, сайт.

Итеративный подход выбран сознательно: базовый вариант (переобучение с
нуля на каждом запуске) не проверяет ни инкрементальность, ни
накопление состояния, а именно они и являются предметом задания.

Пошаговая инструкция: [`github_actions.md`](github_actions.md).

## 14. Логирование

Модуль `logging`, уровень из `config.yaml` (`INFO`), вывод в файл
`training.log` и в консоль. Сообщения о загрузке батчей, качестве,
размерности признаков, дрейфе, решении гейта и сохранении артефактов.
